The Glyph Interchange Format (GLIF) is a simple, human-readable XML representation of a single glyph. Each glyph in a UFO 1 font is stored as a separate `.glif` file inside the `glyphs/` directory, with the mapping between glyph names and file names maintained by `contents.plist`. GLIF version 1 — used throughout UFO 1 — encodes advance metrics, Unicode code points, outlines built from contours and components, and an optional per-glyph data library.

<Note>
  This page documents **GLIF version 1** as used in UFO 1. UFO 3 introduced
  **GLIF version 2**, which adds guidelines, image references, anchors,
  an identifier attribute, and an expanded point model. See the
  [UFO 3 GLIF reference](/ufo3/glif) for the current format.
</Note>

## File Format

GLIF files are plain XML and typically carry a `.glif` extension. There is no DTD; the structure is defined entirely by the element and attribute names described below.

## Element Reference

### `<glyph>` — Top-Level Element

The `<glyph>` element is the document root. It wraps all other GLIF data.

#### Attributes

<ParamField path="name" type="string" required>
  The name of the glyph. Because `contents.plist` is the authoritative mapping
  from glyph names to file names, readers should treat this attribute with
  caution: manual edits may produce a mismatch between the `name` attribute,
  the file name, and the `contents.plist` entry. In practice this attribute is
  often ignored when reading files.
</ParamField>

<ParamField path="format" type="integer" required>
  The GLIF format version. Always `1` for UFO 1 files.
</ParamField>

#### Child Elements

| Element | Occurrences | Purpose |
|---|---|---|
| `<advance>` | 0 or 1 | Horizontal and vertical advance metrics. |
| `<unicode>` | 0 or more | Unicode code point assignments. |
| `<outline>` | 0 or 1 | Outline data (contours and components). |
| `<lib>` | 0 or 1 | Per-glyph custom data storage. |

---

### `<advance>` — Horizontal and Vertical Metrics

Encodes the advance width and optional vertical advance for the glyph. This element has no child elements.

#### Attributes

<ParamField path="width" type="integer or float">
  The horizontal advance width of the glyph in design units.
</ParamField>

<ParamField path="height" type="integer or float">
  The vertical advance of the glyph. Used in vertical layout contexts.
</ParamField>

---

### `<unicode>` — Unicode Code Point

Associates the glyph with a Unicode code point. The element may appear any number of times; the **first** occurrence defines the primary Unicode value for the glyph. This element has no child elements.

#### Attributes

<ParamField path="hex" type="string" required>
  A Unicode code point expressed as a hexadecimal string (e.g. `0041` for
  LATIN CAPITAL LETTER A). Leading zeros are conventional but not required.
</ParamField>

---

### `<outline>` — Outline Description

A container for the glyph's vector outline. The outline may consist of any number of `<contour>` and `<component>` child elements in any order. This element carries no attributes.

#### Child Elements

| Element | Occurrences | Purpose |
|---|---|---|
| `<contour>` | 0 or more | A single closed or open contour. |
| `<component>` | 0 or more | A reference to another glyph inserted into this outline. |

---

### `<component>` — Referenced Glyph Component

Inserts another glyph's outline into the current glyph, optionally transformed by an affine matrix. This element has no child elements.

#### Attributes

<ParamField path="base" type="string" required>
  The name of the base glyph to insert.
</ParamField>

<ParamField path="xScale" type="integer or float" default="1">
  The `xx` component of the transformation matrix.
</ParamField>

<ParamField path="xyScale" type="integer or float" default="0">
  The `xy` component of the transformation matrix.
</ParamField>

<ParamField path="yxScale" type="integer or float" default="0">
  The `yx` component of the transformation matrix.
</ParamField>

<ParamField path="yScale" type="integer or float" default="1">
  The `yy` component of the transformation matrix.
</ParamField>

<ParamField path="xOffset" type="integer or float" default="0">
  The `dx` (horizontal translation) component of the transformation matrix.
</ParamField>

<ParamField path="yOffset" type="integer or float" default="0">
  The `dy` (vertical translation) component of the transformation matrix.
</ParamField>

<Info>
  The six transformation values `xScale xyScale yxScale yScale xOffset yOffset`
  form a standard 2D affine transformation matrix `[xx xy yx yy dx dy]`. The
  default values represent the identity transformation `[1 0 0 1 0 0]`, meaning
  no scaling, rotation, or translation is applied.
</Info>

---

### `<contour>` — Contour Description

Represents a single path, which may be open or closed depending on whether the first `<point>` is of type `move`. The element carries no attributes and contains one or more `<point>` child elements.

#### Child Elements

| Element | Occurrences | Purpose |
|---|---|---|
| `<point>` | 0 or more | An on-curve or off-curve coordinate. |

---

### `<point>` — Attributed Coordinate

A single coordinate within a contour. The combination of `type` values across consecutive points determines the curve segments of the contour.

#### Attributes

<ParamField path="x" type="integer or float" required>
  The x coordinate of the point in design units.
</ParamField>

<ParamField path="y" type="integer or float" required>
  The y coordinate of the point in design units.
</ParamField>

<ParamField path="type" type="string" default="offcurve">
  The point and/or segment type. See the **Point Types** table below.
</ParamField>

<ParamField path="smooth" type="string" default="no">
  Only valid when `type` indicates an on-curve point. Set to `yes` to specify
  that a smooth curvature should be maintained at this point — equivalent to
  a *curve point* or *tangent point* in Fontographer terms.
</ParamField>

<ParamField path="name" type="string">
  An arbitrary label for this point. Names do not need to be unique within a
  contour or outline.
</ParamField>

#### Point Types

| Type | Description |
|---|---|
| `move` | Must be the first point of a contour when present. Signals the start of an **open** contour. A contour without a `move` is a **closed** contour — a cyclic list with no fixed start point. |
| `line` | Draw a straight line from the previous on-curve point to this point. The previous point may be `move`, `line`, `curve`, or `qcurve`, but not `offcurve`. |
| `offcurve` | An off-curve control point that influences the curve segment leading to the next `curve` or `qcurve` point. |
| `curve` | Draw a cubic Bézier curve from the last non-`offcurve` point to this point. Zero preceding `offcurve` points produces a straight line; one produces a quadratic curve; two produces a standard cubic; more than two uses the Super Bézier algorithm. |
| `qcurve` | Similar to `curve` but uses TrueType-style quadratic curves with implied on-curve points. |

---

### `<lib>` — Per-Glyph Custom Data

Stores arbitrary application-specific data at the glyph level. The element's content is an XML property list `<dict>`. To avoid naming collisions, keys should follow the reverse-domain convention defined for `lib.plist` (e.g. `com.example.myapp`). This element may appear at most once.

## XML Examples

### Simple Glyph with a Cubic Outline

The example below shows a period glyph with a single closed cubic contour and an inline lib entry.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<glyph name="period" format="1">
  <advance width="268"/>
  <unicode hex="002E"/>
  <outline>
    <contour>
      <point x="237" y="152"/>
      <point x="193" y="187"/>
      <point x="134" y="187" type="curve" smooth="yes"/>
      <point x="74" y="187"/>
      <point x="30" y="150"/>
      <point x="30" y="88" type="curve" smooth="yes"/>
      <point x="30" y="23"/>
      <point x="74" y="-10"/>
      <point x="134" y="-10" type="curve" smooth="yes"/>
      <point x="193" y="-10"/>
      <point x="237" y="25"/>
      <point x="237" y="88" type="curve" smooth="yes"/>
    </contour>
  </outline>
  <lib>
    <dict>
      <key>com.letterror.somestuff</key>
      <string>arbitrary custom data!</string>
    </dict>
  </lib>
</glyph>
```

### Composite Glyph Using a Component

The following shows how a composite glyph (e.g. `Aacute`) references a base glyph using the default identity transformation.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<glyph name="Aacute" format="1">
  <advance width="600"/>
  <unicode hex="00C1"/>
  <outline>
    <component base="A"/>
    <component base="acutecomb" xOffset="200" yOffset="0"/>
  </outline>
</glyph>
```

### Glyph with Minimal Data

A glyph may omit most elements. The advance and unicode are optional:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<glyph name="space" format="1">
  <advance width="250"/>
  <unicode hex="0020"/>
</glyph>
```

## contents.plist and File Naming

GLIF file names are derived from glyph names using a deterministic algorithm designed to handle case-insensitive file systems. The most common implementation appends a trailing underscore (`_`) to any component of the glyph name that begins with a capital letter.

| Glyph Name | File Name |
|---|---|
| `a` | `a.glif` |
| `A` | `A_.glif` |
| `A.alt` | `A_.alt.glif` |
| `T_H` | `T__H_.glif` |
| `T_h` | `T__h.glif` |
| `f_f_i` | `f_f_i.glif` |
| `F_F_I` | `F__F__I_.glif` |

<Warning>
  File system length limits can cause collisions, and the algorithm assumes
  only the first character of a glyph name is case-significant — names like
  `A.alt` and `A.Alt` will produce the same file name. Always rely on
  `contents.plist` as the authoritative name-to-file mapping rather than
  reconstructing file names algorithmically.
</Warning>
